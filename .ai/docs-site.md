# The docs site — what "the docs page" means

When the user says **"the docs page" / "the docs site"**, they mean the public
**GitHub Pages site** deployed out of this repo's markdown docs:
<https://polynaut.github.io/dth-character-studio/> — a landing page plus the
rendered user guide. It is **not** an in-app route: the app's topbar "Docs"
button (`apps/web/src/components/header-nav.tsx`, `DOCS_URL`) simply opens the
guide externally.

## The pieces

| Piece | Source | Notes |
|---|---|---|
| Landing page | `site/` (`index.html`, `main.js`, `search.js`, `styles.css`) | Plain hand-written static HTML/CSS/JS — no framework, no bundler, no npm deps. Dark-only by design. Design tokens live in `site/styles.css` `:root`. |
| Guide content | `docs/guide/*.md` | **Single source of truth** — the same files render on GitHub. Every page must start with an `# ` title line. |
| Guide build | `scripts/build-guide-site.mjs` (`pnpm build:guide`) | Renders `docs/guide/*.md` → `site/guide/*.html` (gitignored, built at deploy time). Re-skins the markdown with the landing page's styling + a sidebar. |
| Guide chrome | `site/guide.css`, `site/guide.js` | Shared by all generated guide pages (lightbox, anchor copying, sticky headings, direct-download button, click-to-play clips). |
| Docs search | `site/search.js` | ONE file, loaded by BOTH `site/index.html` and every generated guide page (the build script bakes the tag into the shell); path-aware via `body.guide-body`. Styling in `site/styles.css`. |
| Screenshots / clips | `docs/guide/screenshots/`, `docs/guide/clips/` | Generated by the Playwright suite (`apps/web/smoke/guide.screenshots.ts`, `guide.clips.ts`; `pnpm screenshots` / `pnpm clips`) against the real SPA. |

Heads-up: `pnpm lint` covers only `apps packages` — `site/` and `scripts/` are
**not** linted. `site/guide.js`, `search.js` and `main.js` are hand-maintained
plain browser JS; keep them dependency-free.

## Build guards (all fail the build, deliberately)

`build-guide-site.mjs` enforces:

- **NAV placement** — every `docs/guide/*.md` must be listed in the script's
  `NAV` (sidebar order), and every NAV entry must exist on disk.
- **Asset coverage** — screenshots/clips/gifs referenced by a page must exist,
  and none may be orphaned; plus an output-side re-check that each referenced
  asset actually landed in `site/guide/` (catches a dropped `cpSync`).
- **Search extraction** — every page must yield at least one search-index entry
  (see below); zero entries means the heading markup and the index extractor
  drifted apart.
- **Hash links** — every in-guide `href="page.html#id"` / `href="#id"` must
  point at an id that exists in the built target page; a renamed
  heading/accordion (or a changed slug rule) fails the build instead of
  shipping a silently dead deep link.
  - **An `&` in a heading slugifies to `-amp-`, not `-`.** `slugify` runs on the
    RENDERED inline HTML, where markdown-it has already escaped `&` to `&amp;`;
    stripping the non-alphanumerics then leaves the literal word `amp`. So
    `## Tab 1 — Scan & index` is `#tab-1--scan-amp-index` (and the em dash, being
    stripped between two spaces, is why the doubled `--` is there at all). The
    existing `advanced.html#multiple-daz-scenes--outfits-amp-hair-variants` is
    the same shape. Guessing the "obvious" slug for a heading with an `&` fails
    the build — **run `pnpm build:guide` before pushing a doc link**; it is the
    only gate that catches it, and it is NOT part of the `/verify` gate
    (typecheck / lint / test / smoke / cargo all pass with a dead link).
  - **An apostrophe slugifies to the digits `39`** — same mechanism one step
    worse. marked escapes `'` to `&#39;` in the rendered heading, and stripping
    the non-alphanumerics leaves the `39` behind, so
    `## Finding a morph's internal Daz name` is
    `#finding-a-morph39s-internal-daz-name`. Measured 2026-08-17 on the guide
    diet, where the "obvious" `#finding-a-morphs-…` failed the build. Rewrite
    the heading without the apostrophe rather than shipping a link that reads
    like a typo.
  - **`<details>` summaries are anchors too, and they follow the OPPOSITE rule**:
    the accordion post-pass strips entities before slugging, so a summary
    reading `morphs &amp; node` is `#morphs--node` (two dashes, no `amp`). These
    ids are newer than the headings' and carry no GitHub-slug compatibility, so
    the two rules genuinely differ — check which kind of anchor you are linking
    to before writing it.

## Deploy & previews

- **Production**: `.github/workflows/pages.yml` — on `main` push touching
  `site/**`, `docs/guide/**`, or the build script, runs `pnpm build:guide` and
  deploys `site/` to GitHub Pages.
- **PR previews**: `.github/workflows/site-preview.yml` — PRs touching the same
  paths get a Cloudflare Pages preview (`pr-<N>.dth-character-studio.pages.dev`,
  sticky PR comment + GitHub deployment box). Production hosting stays on
  GitHub Pages; Cloudflare only serves previews. Keep the two workflows' `paths`
  lists in sync.

## Guide search

Docs-style client-side search over the whole guide — no external service, no
runtime dependency:

- **Index**: built by `build-guide-site.mjs` into `site/guide/search-index.json`
  — one entry per heading section AND per accordion (`<details>` titles are
  anchorable section titles; folded into a parent body they were unfindable) —
  `{page, title, level, id, heading, text}`, cut from the same rendered HTML
  the pages ship with, so every entry deep-links to a real anchor id. Adding a
  page/section/accordion needs no extra step.
- **UI**: `site/search.js` — shared by the landing page and every guide page
  (`site/index.html` and the generated guide shell both load it; page-relative
  vs `guide/`-prefixed links resolved via `body.guide-body`). Topbar button
  (baked into the shell by the build script), Ctrl/⌘+K or `/` to open, ↑/↓ +
  Enter to navigate, Escape closes.
  Fetches the index once on first open. Scoring: query words AND-match;
  word-start heading hits > heading > page title > body; whole-phrase bonus for
  multi-word queries; small level bonus floats a page's own entry over its
  subsections. Result rows render via DOM nodes + `<mark>` (no innerHTML of
  index text). Styling in `site/styles.css` (`.topbar-search` /
  `.guide-search` / `.search-panel`).
- **Gotcha (measured)**: `str.split(/(?=<h)/)` yields **no** leading empty
  chunk when the string starts at the delimiter — an unconditional `.slice(1)`
  after such a split silently dropped every page's h1 entry. The extractor now
  keeps all chunks and lets the heading regex reject non-heading ones; the
  per-page ≥1-entry guard exists precisely to catch this class of drift.

## Landing teasers must load eagerly (mask + view-timeline kills `loading=lazy`)

Measured 2026-08-18 (Playwright/Chromium, and live on the deployed site): an
`<img loading="lazy">` inside `.section-teaser` is **never requested** — not on
page load, not after scrolling it fully into view. The empty frame still
renders (the container's `aspect-ratio` reserves the space and the `::after`
ring draws), so the failure looks like a broken image URL when the URL is fine.
Isolated by matrix test: the container's `mask-image` fade **combined with**
the `@supports (animation-timeline: view())` entrance animation makes
Chromium's lazy-loader treat the img as invisible; either effect alone
lazy-loads normally. Consequence: the two landing teaser imgs carry no
`loading` attribute (eager) — don't "optimize" it back on, and any NEW teaser
img added under that CSS must stay eager too. Guide pages are unaffected
(`guide.css` has neither mask nor scroll-driven animations).

## Clips are click-to-play on the SITE only

The four `docs/guide/clips/*.webp` are **animated** WebPs, and an animated WebP
has no pause API — as a plain `<img>` each one loops at the reader for as long
as the page is open (three of them at once on `advanced.md`). There is no CSS
route either: `animation-play-state` governs CSS animations, not decoded image
frames. The only mechanism is to show a still and swap the `src`.

Three pieces, and they only work together:

- **`webp-recorder.ts`** writes `<name>.poster.webp` — frame 0 as a still —
  beside every clip it saves. Done there, not at build time, because frame 0 is
  already in hand and `build-guide-site.mjs` deliberately carries **no image
  library** (it sniffs dimensions by magic number).
- **`clickToPlayClips`** in `build-guide-site.mjs` rewrites each clip `<img>` to
  `<span class="clip" data-clip="<animated>"><img src="<poster>"><button
  class="clip-play"></button></span>`. It runs **before** `reserveImageSpace`,
  so the aspect ratio is stamped from the file actually loaded.
- **`site/guide.js`** swaps `src` between poster and clip on click. Re-assigning
  `src` is what restarts an animated WebP from frame 0, so a replay always
  begins at the beginning. Starting one clip stops any other.

**Why the transform is at BUILD time and not in the markdown:** `docs/guide/*.md`
is the single source of truth and also renders **on GitHub**, where no script of
ours runs. Left as a plain `<img>` there, a GitHub reader still gets the clip as
before; only the built site gains the button. Putting the wrapper markup in the
markdown would trade the site's problem for a GitHub page showing a dead still.

Two consequences worth knowing before touching this:

- The poster is **referenced exactly when its clip is** — the build's clip guard
  derives it, so a missing poster fails the build and a stale one is an orphan,
  same as any other asset. Never hand-author one; re-run `pnpm clips`.
- **Clips no longer open the lightbox.** `guide.js` bails on `.clip` before the
  lightbox handler, because one click cannot mean both "play" and "zoom".

## Anchor landing & image layout shift

Deep links (`page.html#section` — hand-shared or from search) used to land
"randomly": the browser scrolls before the big screenshots load, then each
finished image pushes the target down. Two-part fix, keep both halves intact:

- **Build time**: `reserveImageSpace` in `build-guide-site.mjs` stamps EVERY
  `<img>` with `style="aspect-ratio: W / H"` — local assets
  (screenshots/clips/gifs) read from disk, external ones (GitHub
  user-attachments URLs) fetched once per build. Dimensions come straight from
  the image bytes, sniffed by magic number (PNG IHDR, GIF logical screen, WebP
  VP8X/VP8/VP8L) — no image library. Boxes get their height at first paint, so
  the native anchor scroll is already exact. A failed external fetch only warns
  (never fails the build) and skips that stamp.
- **Load time**: `revealHashTarget` in `site/guide.js` re-scrolls the visited
  hash after `load` (and opens a targeted accordion) — the fallback for an
  external image whose build-time fetch failed.
- **Sticky-chrome clearance is MEASURED, not fixed**: an anchor inside a
  section must land below the docked chapter title, and that title WRAPS to
  2-3 lines on narrow viewports — a fixed `scroll-margin-top` hid h4 targets
  on phones. `setAnchorClearance` (guide.js) measures each section's own h2
  and sets per-element margins, re-run before every reveal and on resize; the
  stylesheet's fixed values remain only as the no-JS fallback. Every id'd
  heading level (h3-h6) and accordion needs this clearance — h4s were missed
  once already.
